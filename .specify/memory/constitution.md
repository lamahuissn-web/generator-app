# Generator Manager Constitution

A subscriber-billing panel for a private electricity generator in Lebanon: meter readings,
monthly invoices, cash collection in the field, expenses, and the ledger behind them. The office
works in Arabic, the ledger is in dollars, and the money is counted by hand at the end of a day.
Every rule below exists because getting it wrong costs the operator money or an argument at a
customer's door.

## Core Principles

### I. Bilingual Parity, and the Numbers Never Change

Every user-visible string exists in BOTH catalogues (`lang/ar.json`, `lang/en.json`); a key added
to one MUST be added to the other in the same change. Counted labels MUST go through the `plural()`
helper and carry the six CLDR Arabic forms (zero/one/two/few/many/other) — never `:n` glued to a
singular noun. Digits stay Western Latin (`0-9`) and money stays `$` in Arabic as well as English;
a Latin run dropped into Arabic prose (an amount, a meter number, a date, a reading pair) MUST be
wrapped with `ltr_isolate()` / `money_ltr()` so bidi cannot strand it from its label. Rationale:
the office reads Arabic, the paper is dollars, and "10" rendered in Arabic-Indic digits is a figure
nobody can reconcile against a printed receipt.

### II. One Description of Every Rule

A domain rule lives in exactly one place: `App\Services\*` for behaviour (billing, collection,
handovers, the cycle lock, currency) and `App\Reports\*` for reader-facing truth (worklists,
aged debt, a subscriber's file). Screens, tables, exports, print views and the public site compose
those; they MUST NOT recompute a total, a status, a coverage figure or an age. A rule two screens
share is exposed once — a public static method on the owning service — and read by both, so the two
can never disagree. The same applies to structure: a field's visibility, a table's columns and an
action's behaviour are declared once (`FormDefinition`, `TableDefinition`, `ActionDefinition`) and
rendered everywhere from that declaration. Rationale: the panel's only credibility is that every
screen gives the same answer to the same question.

### III. Tests Are the Definition of Done (NON-NEGOTIABLE)

A behavioural change ships with a test that FAILS without it; verify by reverting the fix and
watching the suite go red before claiming success. When a defect reveals a CLASS of bug, the
regression test MUST be written against the class — generated by iterating the registry or the
screen definitions where possible — not only the reported site. The full suite (`php artisan test`)
MUST pass before a phase is committed, and it runs against in-memory SQLite only: `tests/TestCase.php`
refuses any other connection, because `RefreshDatabase` wipes whatever it is pointed at. Rationale:
400+ assertions are the only reason a two-month-old ledger, edited by several hands, can be trusted.

### IV. Nothing Fails Silently

A refusal is a business rule, not a crash: a domain service throws `RuntimeException` and the
calling screen catches it and shows the service's own wording next to the control that caused it —
never a 500, and never a button that appears to do nothing. A write action MUST be reachable by a
visible control on the screen that owns it; a route with no link is not a feature, and a validation
rule MUST NOT be able to fire for a field the operator cannot see (a field inside a hidden section
contributes no rules). Corrections to a closed cycle, a paid invoice or a locked reading MUST record
who made them and why through `Audit`, and require an admin where `CycleLock` says so. Rationale:
the office has no console to read — if the panel does not say it, the operator cannot know it.

### V. Exact Money, and the Paper Adds Up

Amounts are stored as `decimal(12,2)` and rounded ONLY where the office decided (the invoice
rounding setting); no view rounds a figure, and the printed document's own lines MUST sum to the
total it prints. The ledger stays in dollars: a collection in lira is converted once through
`App\Services\Currency`, and the receipt stores both the lira that changed hands and the rate it was
taken at, so a later rate cannot restate an earlier month. A closed cycle is history — it can be
corrected, but only deliberately, with an admin and a written reason. Rationale: a receipt from
August must still say what August was worth, and an invoice whose consumptions do not add up is an
argument at the door.

## Additional Constraints

- **Stack**: PHP 8.2+ on Laravel 12, Livewire 4, MySQL in development. Tests run on in-memory
  SQLite via `phpunit.xml`. Do not add a runtime dependency without a written reason in the plan:
  the panel must stay deployable on a cheap host with `composer install` and no build step.
- **Styling**: Metronic 9.5 precompiled assets. The shipped CSS contains only the utilities
  Metronic's own demos use, so a new utility class MUST be verified against the built stylesheet
  (`public/build/assets/app-*.css`) before it is relied on — a missing class fails silently as an
  unstyled element. Prefer the panel's own components (`x-admin.card`, `x-admin.table`,
  `x-admin.field`, `x-admin.stat`) over hand-rolled markup.
- **Schema**: every migration MUST be reversible, and a migration that rewrites existing rows MUST
  state in its own comment what it does to data already in the ledger.
- **Previews**: server-rendered page dumps for visual review live in `public/_preview/`, which is
  gitignored. Never commit generated HTML, screenshots, or `_preview` output.

## Development Workflow

- Non-trivial work runs through the Spec Kit loop (`spec → plan → tasks → implement → converge`);
  its artifacts live under `specs/NNN-slug/`. Small fixes — a typo, a one-line correction — use the
  ordinary edit-and-test path instead; the workflow is not a tax on trivia.
- Work is delivered PHASE BY PHASE. A phase ends with: the full suite green, a short report of what
  changed and what was verified, and the explicit next steps. Commits are written as prose that
  explains WHY (the mechanism and the decision), and they are made, pushed or history-rewritten ONLY
  when the operator says so.
- The operator reviews Arabic screens before a phase is committed; a screenshot or a
  `public/_preview/*.html` page is part of the evidence, not a nicety.
- A phase that changes how the office works MUST be checked against the paper: what the receipt,
  the invoice, the statement and the printed list will say after the change.

## Governance

This constitution supersedes other practices where they conflict. Amendments are made by running
the constitution step of Spec Kit (`speckit-constitution`), which MUST: update the version line,
record a Sync Impact Report for human review, and keep every principle declarative and testable.
Versioning is semantic: MAJOR for removing or redefining a principle, MINOR for adding one or
materially expanding guidance, PATCH for clarifications that change no expectation.

Compliance is checked at two gates that already exist in the loop: the plan's constitution check
(before implementation) and the analyze step (before implementation resumes after an amendment).
A conflict with a MUST in this document is a CRITICAL finding and blocks implementation until the
spec, the plan or the code is corrected. Every feature's `plan.md` MUST name the principles it
touches and how it satisfies them; complexity that cannot be justified against a principle is
refused rather than documented.
